# SYNTARO Growth Initiative — Phase 5: The 1M-User Path (Phased Milestones)

> **Status**: Roadmap (strategy document)
> **Owner**: SYNTARO Growth Initiative (AIM-4370)
> **Objective**: Define the phased roadmap from launch to **1,000,000 users**, with the milestones, gates, and exit path that make each phase independently fundable.

This document is the master roadmap for the 1M-user path. It decomposes the journey into four phases with explicit milestone checklists, the key metric each phase must clear before the next one starts, and the engineering and economic preconditions (from [`UNIT_ECONOMICS.md`](../../UNIT_ECONOMICS.md) and [`SCALING.md`](../../SCALING.md)) that must hold at each step. It is deliberately concrete: every phase names the acquisition channel, the viral mechanics, the team-size implications, and the fail-gate.

## The Shape of the Journey

```
Phase 1            Phase 2            Phase 3            Phase 4
M1–M3              M3–M6              M6–M12             M12–M18
0 → 10K            10K → 100K         100K → 500K        500K → 1M
─────────────      ─────────────      ─────────────      ─────────────
Marketplace        Viral loop         Featured           Enterprise
+ PR footer        k ≈ 0.3–0.5        Marketplace        + compliance
+ HN/PH launch     OSS community      + enterprise       + partnerships
                   + content engine   + GitLab/Bitbucket
```

Each phase is sized so that **the growth mechanism of the phase is the one that produces the phase's numbers**. Phase 1 is launch-driven (one-shot channels plus the first persistent loop). Phase 2 is compounding-driven (the viral loop must carry the growth alone). Phase 3 is breadth-driven (new platforms + enterprise motion). Phase 4 is trust-driven (compliance, status checks, partnerships).

---

## Phase 1 — M1–M3: 0 → 10,000 users (Launch)

**Objective**: Validate that the product-market fit observed in the flywheel design holds in the wild, and get the persistent viral loop installed in front of real traffic.

### Milestone checklist

- [x] **Marketplace listing** — GitHub Marketplace listing live (`docs/marketplace-listing.md`, verified-publisher guide). This is the P0 acquisition channel: $0 cost, very high volume, high conversion.
- [x] **PR footer** — "This fix was automatically generated by SYNTARO" footer on every bot PR (the persistent viral loop; every PR becomes an ad impression).
- [ ] **HN launch** — Hacker News launch post (`docs/hn-launch-post.md`). One-shot traffic spike; expect 300–1,000 installs from the spike and, more importantly, the first social proof.
- [ ] **Product Hunt launch** — Product Hunt listing (`docs/product-hunt-launch-kit.md`). Second one-shot spike; dev-tool PH launches historically convert 5–15% of upvotes into installs.

### Growth mechanism

Linear-plus: one-shot channels (HN, PH) provide the initial base; the PR footer loop starts compounding from day one. Per the 90-day plan, the PR footer loop alone targets **k ≈ 0.20** in this phase.

### Key metrics / fail-gates

| Metric | Target by M3 | Why it matters |
|---|---|---|
| Cumulative installs | 2,500–10,000 | Phase 1's definition of done |
| Free → paid conversion | ≥ 5% | Must clear the dev-tools median (3–5%) before scaling paid motion |
| Fix merge rate | ≥ 55% | The PR footer only compounds if merges keep happening (trust) |
| Median label → PR time | < 10 min | "Wow" moment must be fast |
| MRR | ~$6K–$10K | Sanity check against unit economics (Solo $49 / Team $149) |

**Gate into Phase 2**: installs ≥ 10K **and** conversion ≥ 5% **and** merge rate ≥ 55%. If the fix quality bar isn't met, the viral loop will compound *distrust* — do not scale a broken loop.

## Phase 2 — M3–M6: 10K → 100,000 users (Compounding)

**Objective**: Make the product itself the growth engine. All three levers below feed the same viral loop; the loop must reach **k ≈ 0.3–0.5**.

### Milestone checklist

- [ ] **Viral loop k ≈ 0.3–0.5** — the PR footer + team-invite + content loops mature from k ≈ 0.20 to the 0.30–0.50 band (90-day plan Q2/Q3 targets). At k = 0.4 with a ~2-week viral cycle, 10K → 100K is ~7 cycles ≈ 3.5 months — inside this window. At k = 0.3 it is ~9 cycles ≈ 4.5 months (tight, needs the content engine to close the gap).
- [ ] **OSS community** — open-source the integration surface / community edition hooks (plugins, templates). This is the Renovate-style play: OSS reputation feeds Marketplace discovery and star-to-install funnel.
- [ ] **Content engine** — every successful fix is a potential case study ("How SYNTARO fixed this" pages, benchmark posts). Per the 90-day plan, content contributes k ≈ 0.05–0.10 on its own.

### Growth mechanism

Compounding. This is the only phase where the k-factor must carry the entire 10×. Team invite loops (k ≈ 0.10) and content sharing (k ≈ 0.10) must come online this phase — the PR footer alone (k ≈ 0.20) cannot produce 10× in 3 months.

### Key metrics / fail-gates

| Metric | Target by M6 | Why it matters |
|---|---|---|
| Cumulative installs | 100,000 | Phase 2's definition of done |
| Combined k-factor | ≥ 0.3 (stretch 0.4+) | The single number this phase exists to move |
| Active repos (monthly) | ≥ 8,000 | Proves installs are usage, not curiosity |
| Time-to-fix (median) | < 7 min | Speed is the differentiator vs Plip/KintsugiBot |
| Churn | ≤ 5% | Below dev-tools median; churn kills compounding |
| NDR | ≥ 110% | Team expansion (seat/usage growth) must be real |
| MRR | ~$50K–$100K | Reflects conversion + expansion at 100K scale |

**Gate into Phase 3**: installs ≥ 100K **and** k ≥ 0.3 **and** churn ≤ 5%. If k stays below 0.3 after the OSS + content investments, the model is broken — fix the loop before spending on enterprise motion.

**Engineering precondition**: this phase must start the [`SCALING.md`](../../SCALING.md) Phase 2 transition (single box → Celery fleet with RabbitMQ task distribution) before the 100K user mark; per-fix costs must follow the [`UNIT_ECONOMICS.md`](../../UNIT_ECONOMICS.md) Phase 2 cost-reduction path or the growth will be margin-negative.

## Phase 3 — M6–M12: 100K → 500,000 users (Breadth)

**Objective**: Diversify acquisition beyond the viral loop — new platforms, new buyer motion, Marketplace prominence — so growth no longer depends on a single mechanism.

### Milestone checklist

- [ ] **Featured Marketplace** — apply for / earn GitHub Marketplace "Featured" status (quality bar, install volume, review rating). Featured apps get disproportionate Marketplace surface area; this is a step-change in the P0 channel.
- [ ] **Enterprise features** — SSO, audit log, VPC/dedicated inference, SLA support (the Enterprise tier from the 90-day plan). Unlocks the org buyer and the compliance conversation that Phase 4 monetizes.
- [ ] **GitLab / Bitbucket** — port the GitHub app to GitLab and Bitbucket. 100K GitHub users is a large but saturated slice of the market; GitLab/Bitbucket add 30–50% addressable market headroom.

### Growth mechanism

Breadth + enterprise motion. Organic k decays as the base grows (same loop, bigger base); the phase's growth comes from **new channels** (new platforms, featured surface area) and **new buyer motion** (enterprise sales). 5× in 6 months is achievable with k ≈ 0.5 organic plus two new channels — but it requires the enterprise pipeline to start producing by M9.

### Key metrics / fail-gates

| Metric | Target by M12 | Why it matters |
|---|---|---|
| Cumulative installs | 500,000 | Phase 3's definition of done |
| Enterprise accounts | ≥ 20 | Proof the enterprise motion works before Phase 4 bets on it |
| Non-GitHub share of installs | ≥ 10% | Validates the platform diversification |
| Fix completion rate | ≥ 80% | Marketplace featured bar + enterprise diligence both need this |
| NDR | ≥ 125% | Enterprise expansion economics |
| MRR | ~$150K–$400K | Linear interpolation between 90-day Q3/Q4 projections |

**Gate into Phase 4**: installs ≥ 500K **and** ≥ 20 enterprise accounts **and** non-GitHub share ≥ 10%. If enterprise adoption is zero at M12, Phase 4's compliance/partnership play is built on sand — reassess before spending on SOC2 marketing.

**Engineering precondition**: cost reduction to [`UNIT_ECONOMICS.md`](../../UNIT_ECONOMICS.md) Phase 3 (scale) costs — breakeven at scale. Enterprise VPC/dedicated inference demand per-tenant isolation that the Celery fleet must be restructured to support.

## Phase 4 — M12–M18: 500K → 1,000,000 users (Trust & Bundles)

**Objective**: Cross the 1M mark by making SYNTARO the *default* fix pipeline rather than the *chosen* one — required status checks, compliance bundling, and channel partnerships convert the long tail of conservative adopters.

### Milestone checklist

- [ ] **Required status checks** — SYNTARO as a mandatory status check in org policies (the Dependabot pattern: once a tool is a required check, it is no longer optional; it rides every PR). This is the single highest-leverage conversion of *users* to *necessity*.
- [ ] **Compliance bundling** — bundle SOC 2 reports, audit logs, and regional (EU/GDPR — see `docs/gtm/germany-eu-taas-market-analysis.md`) compliance artifacts into paid tiers. Compliance is a buying trigger for the conservative majority that the viral loop never reaches.
- [ ] **Partnerships** — cloud vendor marketplaces (AWS Marketplace, Azure, GCP), CI/CD ecosystem bundling, and agency/consultancy distribution. Partnerships convert the channels that won't organically install.

### Growth mechanism

Trust-driven conversion + distribution partnerships. Organic k is now secondary (large base, low per-user compounding); the 2× to 1M comes from *required* adoption (status checks), *compliance-gated* purchases (bundles), and *partner-sold* seats. 2× over 6 months is the easiest multiple of the whole roadmap *if* the Phase 3 enterprise foundations exist — and the hardest if they don't.

### Key metrics / fail-gates

| Metric | Target by M18 | Why it matters |
|---|---|---|
| Cumulative users | 1,000,000 | Phase 4's definition of done (the objective of this document) |
| % of org installs with SYNTARO as required check | ≥ 30% | The "default, not chosen" signal |
| Compliance-tier accounts | ≥ 5% of paid | Validates the bundling thesis |
| Partner-sourced installs | ≥ 15% | Distribution diversification |
| ARR | ~$25M–$40M (3% conversion × ~$75/mo blended) | The number the exit conversation is priced on |

**Gate into exit**: users ≥ 1M **and** ARR ≥ $25M **and** required-check penetration ≥ 30%. At this point the company is either a top-tier acquisition target or a fundable scaled company — see next section.

## Exit Path Planning

The parent initiative's research (AIM-4370) is unambiguous about precedent: **the Dependabot path is the proven outcome for a viral GitHub App**. Dependabot reached millions of repos and was acquired by GitHub (2019, undisclosed) — the acquirer *is* the distribution channel, and the acquisition is effectively the platform internalizing its top ecosystem tool. Renovate (16K stars, same category) followed the OSS→acquired path via WhiteSource/Mend (2021). CodeRabbit is the current Marketplace leader on the same playbook. Sweep AI's failure was **unit economics, not market** — which is exactly why every phase in this roadmap is gated on `UNIT_ECONOMICS.md` margins rather than raw install counts.

### Path A — Acquisition (Dependabot path) — preferred

**Thesis**: SYNTARO becomes the default fix pipeline for the platform it runs on. At 1M users / ~$25M–$40M ARR, the strategic value to GitHub (or GitLab, or a CI/CD incumbent) is platform lock-in, not revenue.

| Element | Detail |
|---|---|
| Timing | Initiate conversations at M12 (500K users), close window M18–M24 |
| Buyers | GitHub (most likely — Dependabot precedent, same distribution channel), GitLab, Atlassian/Bitbucket, CI/CD incumbents |
| Valuation anchor | 5–10× ARR at $25M–$40M ARR → **$125M–$400M directional range** (marked as estimate, not a comparable-based claim — no disclosed deal terms exist for Dependabot/Renovate) |
| What must be true | Required-check penetration ≥ 30% (defaultness), clean unit economics, single-team-pullable codebase, no IP entanglements |
| Risk | Acquirer doesn't materialize → fall through to Path B |

### Path B — VC-funded scale

**Thesis**: 1M users at 3% conversion is a $25M–$40M ARR company growing at the compounding rate established in Phase 2 — a fundable Series A/B story with a clear path to $100M ARR.

| Element | Detail |
|---|---|
| Timing | Raise Series A at M12–M18 (1M users is the proof point); growth capital M18+ |
| Round logic | ARR $25M–$40M, growth from a *mature* k ≈ 0.3–0.5 loop + enterprise motion → typical late-A/B or Series C multiples (5–10× ARR) |
| What must be true | NDR ≥ 125%, churn ≤ 3%, enterprise pipeline ≥ 20 accounts, partner channel producing ≥ 15% of installs |
| Use of funds | GitLab/Bitbucket depth, EU/GDPR compliance expansion (see `docs/gtm/germany-eu-taas-market-analysis.md`), sales team, multi-region infra |
| Risk | Dilution + the unit-economics trap that killed Sweep AI — mitigated by the margin gates in every phase above |

### Exit decision rules

1. **M12 checkpoint**: if ≥ 2 strategic acquirer conversations are active AND required-check penetration is tracking ≥ 30% → bias Path A.
2. **M18 checkpoint**: if no credible acquisition offer has emerged → bias Path B and start the raise immediately (momentum, not revenue, is what the raise sells).
3. **Any phase**: if the margin gates fail (per-fix cost above breakeven at scale), pause growth spend until unit economics are fixed — an unprofitable viral loop is how the category's graveyard (Sweep AI, Imgbot post-acquisition) is populated.
