# Day 13 — X Retrospective Thread

---

**Tweet 1/7**
Two weeks of office-oxide-mcp. Raw numbers and honest reflections.

A thread on what worked, what didn't, and what I'd do differently. 🧵

**Tweet 2/7**
What worked:
- Rust-first approach was the right call (speed speaks for itself)
- MCP protocol made integration trivial (works everywhere, same API)
- Self-hosted positioning resonated (compliance concerns are real)
- Small tool surface (8 tools, learnable in minutes)
- Community builds got more engagement than technical content

**Tweet 3/7**
What didn't work:
- Launch thread on X got decent reach but low conversion
- Documentation was too technical (need more "getting started" examples)
- Should have had the template library ready at launch
- npm package discovery is poor (people search "office mcp" and don't find it)
- Should have submitted to MCP directories on day 1

**Tweet 4/7**
Surprise hits:
- The Excel query API got way more use than Word editing
- People use it for data extraction (read Excel → JSON) more than document creation
- The PDF merge tool is used in unexpected ways (assembling report packages, merging invoices)
- Template system adoption is 3× what I expected for a "nice to have" feature

**Tweet 5/7**
What I'd do differently:
- Ship the template library before launch (would have driven more Word doc creation use cases)
- Record a 30-second demo video (showing an agent actually processing docs)
- More "compare with cloud alternatives" content (cost savings are the best hook)
- Start the Discord earlier (community conversation drives more engagement than one-way posts)

**Tweet 6/7**
Lessons for other MCP server builders:
- Find a specific pain point, don't build "MCP for everything"
- Performance benchmarks are your best marketing asset
- Community builds are worth more than your own content
- Directory submissions matter more than social media
- The tool surface should be small enough to fit in one screenshot

**Tweet 7/7**
