Getting Started

Installation & first steps

SYNTARO is an AI-powered GitHub bot that reads your repository, analyzes issues, creates a detailed plan, and opens a pull request with the fix. Unlike Copilot or Cursor which provide inline suggestions, SYNTARO works asynchronously — label an issue with syntaro:fix and it handles the full fix cycle autonomously: root cause analysis → plan → implementation → PR.

GitHub Copilot is a reactive code completion tool — it suggests code as you type. Cursor is an AI-native IDE with inline chat. Devin is a fully autonomous AI software engineer at $500/month. SYNTARO sits in a unique middle ground: it's an asynchronous senior architect that reads your entire repo, plans before coding, and opens a PR — but unlike Devin, it's affordable (€0-€49/month) and open source (AGPL v3). All these tools are complementary to SYNTARO.

Visit the SYNTARO GitHub App page, select your repository (or all repositories), and complete the installation. No CLI, no SDK, no configuration file needed. Once installed, just label an issue with syntaro:fix and SYNTARO will handle the rest. Full walkthrough in the Quick Start guide.

No. SYNTARO runs as a GitHub App — there is nothing to install on your machine. Simply install the app from the GitHub Marketplace and grant it access to your repositories. All processing happens on SYNTARO servers (or your infrastructure if self-hosting).

Typical fix time is ~60 seconds from labeling to PR creation. For Pro and Team subscribers with priority queue access, this drops to ~20 seconds. Actual time varies based on repository size, issue complexity, and current queue depth. Monorepos with extensive test suites may take longer.

Yes. The Free plan covers public repositories only. The Pro plan (€19/month) includes private repositories. The Team plan (€49/month) extends this to organization-wide private repositories. You only grant access to specific repositories during installation.

When SYNTARO fixes an issue, it creates a pull request containing: (1) a detailed plan document explaining the root cause and approach, (2) the code changes implementing the fix, (3) a comprehensive PR description summarizing the changes, and (4) test results confirming the existing test suite passes with the new code. You can review everything before merging.

Technical

Architecture, languages & integration

TypeScript and JavaScript are first-class citizens with the best support. Python support is good and actively improving. Rust, Go, and Java support is in active development. As a rule of thumb: if your project has a test suite that SYNTARO can run, it can fix it. The underlying engine (OpenCode) supports any language with a test framework.

SYNTARO performs a multi-step analysis: (1) clones the repository, (2) parses the Abstract Syntax Tree (AST) of each file, (3) builds a dependency graph to understand import/require relationships, (4) runs git blame to identify recently changed files relevant to the issue, and (5) optimizes the context window by prioritizing the most relevant files. This provides SYNTARO with a comprehensive understanding of your codebase while respecting LLM context limits.

Yes. SYNTARO has configurable scope boundaries for monorepos. You can use a .syntaroignore file to exclude specific directories or define focus areas. For large monorepos, SYNTARO prioritizes files most relevant to the issue based on dependency analysis and git history, making the analysis feasible even with context window constraints.

No. SYNTARO always produces a detailed plan first. Only after you explicitly approve the plan does it generate the code and open a pull request. The PR is opened as a draft — you review before merging. You maintain full control at every step. This plan-first approach is a core design principle, not a feature toggle.

Yes. SYNTARO runs your entire test suite as part of the fix pipeline. A fix is only accepted if: (1) all existing tests pass with the new code, (2) any new tests added for the fix also pass, and (3) there are no regressions. If tests fail, the issue remains open with a detailed comment explaining what went wrong.

PRs are opened as drafts — you review before merging. SYNTARO runs the test suite before opening a PR, so known regressions are caught. The current fix rate across 500+ public repository issues is 92%. If a fix is incorrect, close the PR and reopen the issue with additional context. Each failure helps improve future fix quality.

SYNTARO works alongside your existing CI/CD — it doesn't replace it. SYNTARO runs your test suite before opening a PR, but your CI pipeline still runs on the PR as normal. This provides a double validation layer. SYNTARO also supports a GitHub Action for deeper integration.

Security & Privacy

Data protection, compliance & access

SYNTARO processes your code ephemerally. The repository is cloned for analysis and fix generation, but code is not stored long-term. Fix history is retained for 30 days after generation for audit purposes. Pull requests and associated code live on GitHub as standard PRs — you control their lifecycle there.

For cloud-hosted SYNTARO: data is processed in US or EU regions based on customer location at signup. EU customers are routed to EU servers (Hetzner, Germany). For self-hosted deployments: data stays entirely within your infrastructure. We provide a Data Processing Agreement (DPA) for EU customers upon request.

SOC 2 Type I certification is in progress with a target completion within 6 months. ISO 27001 is planned for the following quarter. Enterprise customers can request our current security documentation and penetration testing results via sales@aimino.io.

No. SYNTARO only accesses repositories you explicitly grant access to during the GitHub App installation. You can select specific repositories or all repositories. Access can be revoked at any time from your GitHub settings. SYNTARO never accesses repositories outside its granted scope.

When you uninstall the SYNTARO GitHub App: (1) all access tokens are immediately revoked, (2) fix history is exported and available for 30 days, (3) any in-progress fixes are cancelled, (4) existing PRs opened by SYNTARO remain on GitHub for you to review and merge. No code is retained on SYNTARO servers after uninstallation.

Yes. All data in transit uses TLS 1.3. Data at rest is encrypted using AES-256. Repository data processed during fix generation is stored in memory and not persisted to disk beyond temporary working directories which are cleaned after each run.

Troubleshooting

Common issues & solutions

Check the following: (1) Did you label the issue with syntaro:fix? SYNTARO only responds to the label, not comments. (2) Is the repository in the list of allowed repos? Check your GitHub App settings. (3) Have you hit your monthly fix limit? Check your plan status. (4) Is SYNTARO experiencing an outage? Check status.syntaro.aimino.io. If none of these apply, open a GitHub issue with your repository details.

When a fix fails, SYNTARO posts a detailed comment explaining why. Common reasons: (1) test suite failures — review the test output in the comment, (2) dependency resolution issues — confirm your dependencies are accessible, (3) context window exceeded — very large files may need a .syntaroignore entry. If the error is unclear, open a GitHub issue with the failure comment link.

Plan quality typically depends on: (1) issue description clarity — vague issues yield vague plans. Be specific about expected behavior vs actual behavior. (2) Repository size — very large repos may have context gaps. Use .syntaroignore to focus on relevant directories. (3) Language maturity — some languages have better support than others (see language support above). You can provide feedback on the plan before SYNTARO proceeds to implementation.

After installing the GitHub App, SYNTARO needs a few minutes to sync repository access. If the issue persists: (1) Confirm the installation completed successfully in your GitHub settings (Settings → Applications → SYNTARO). (2) Ensure the repository is listed in the "Repository access" section of the app settings. (3) Try uninstalling and reinstalling the app with explicit repository selection.

Merge conflicts can occur if the repository changed between issue labeling and fix generation. To resolve: (1) Check if you can merge via GitHub's web interface (simple conflicts). (2) Pull the branch locally and resolve conflicts manually. (3) Label the issue again with syntaro:fix and SYNTARO will regenerate the fix against the latest main branch — this doesn't count as a new fix if within 24 hours.

Open a GitHub issue with: (1) the repository URL and issue number, (2) what SYNTARO produced (link to the PR or plan comment), (3) what you expected instead, and (4) any relevant context. Our team reviews all bug reports and uses them to improve fix quality. You can also join our Discord community for faster help.

SYNTARO operates with a fair-use queue. Free tier users may experience longer wait times during peak hours. Pro and Team subscribers get priority queue access (~20s average vs ~60s). If you consistently experience slow processing, check our status page for any ongoing incidents or consider upgrading your plan.

⚡ Troubleshooting Best Practices

  1. Be specific in your issue description. "The login button doesn't work" is less helpful than "The login button throws a 500 error when submitting valid credentials. Expected: redirect to dashboard. Actual: spinner spins indefinitely then shows error toast."
  2. Include error messages and logs. SYNTARO works best when it has concrete error output to analyze. Paste stack traces, console errors, or test failures.
  3. Use .syntaroignore for large repos. Exclude vendor directories, generated code, and build artifacts to help SYNTARO focus on relevant code.
  4. Keep your test suite healthy. SYNTARO validates fixes by running tests. A broken or flaky test suite reduces fix reliability.
  5. Check the plan before approving. SYNTARO always produces a plan first. Review it carefully — if the approach seems wrong, provide feedback in the issue before SYNTARO proceeds.
